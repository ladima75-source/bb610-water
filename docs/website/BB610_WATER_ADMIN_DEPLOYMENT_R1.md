# BB610 WATER — ADMIN DEPLOYMENT R1

## Deployment boundary
TASK 18 prepares non-production deployment only. Live `water.bb610.com.ua`, production DNS/CNAME and root production files must not change until a separate owner-approved cutover.

## Required services
- PostgreSQL 16+ durable instance;
- container/runtime for `services/water-admin-api/`;
- HTTPS reverse proxy / ingress;
- approved Admin origin;
- secret storage for database/JWT/bootstrap values.

## Environment
Required variables are documented in `services/water-admin-api/.env.example`.

Production values must be injected securely. Do not commit `.env`.

At minimum configure:
- `BB610_ADMIN_DATABASE_URL`;
- `BB610_ADMIN_JWT_SECRET`;
- `BB610_ADMIN_JWT_ISSUER`;
- `BB610_ADMIN_JWT_TTL_MIN`;
- `BB610_ADMIN_LOGIN_MAX_FAILURES`;
- `BB610_ADMIN_LOGIN_BLOCK_MIN`;
- `BB610_ADMIN_BOOTSTRAP_EMAIL`;
- `BB610_ADMIN_BOOTSTRAP_PASSWORD`;
- `BB610_ADMIN_CORS_ORIGINS`.

## Review deployment
1. Create a local/private `.env` from `.env.example`.
2. Set strong unique values for all credentials/secrets.
3. Run:
   `docker compose --env-file .env -f docker-compose.review.yml up --build`
4. Container runs `alembic upgrade head` before API startup.
5. Verify `GET http://localhost:8080/health`.
6. Serve repository root on `http://localhost:8000`.
7. Open `http://localhost:8000/docs/website/admin/review/v2/`.
8. Login with the bootstrap account from the private `.env`.
9. Create named operator accounts through admin API/UI workflow.
10. Rotate/remove bootstrap credentials after real accounts exist.

## Production hardening gate
Before production activation:
- TLS only;
- restrict API/Admin network exposure as appropriate;
- restrict CORS to exact approved Admin origin(s);
- database backup schedule active;
- database restore drill passed;
- monitoring for API/database failures;
- strong JWT secret generated by secret manager;
- bootstrap password rotated/disabled;
- named users with least-privilege roles;
- login throttling tested;
- stale version conflict tested;
- audit storage retention policy confirmed.

## Public data cutover
Do not point live WATER at the API in TASK 18.

After separate approval:
1. deploy API/public endpoint;
2. verify published catalog matches approved production data;
3. configure live site public commercial endpoint;
4. retain last-known-good/fallback behavior;
5. publish a no-op/known test change in controlled window;
6. verify buyer configurator output;
7. verify rollback to prior published version;
8. monitor.

## Rollback of deployment
Application rollback and commercial-data rollback are separate:
- application: redeploy prior container/image;
- commercial data: Admin rollback creates a new published catalog version from a historical snapshot;
- database disaster recovery: use documented PostgreSQL restore procedure.
